CapturePack 플러그인 시스템 재설계 프롬프트
아래 내용을 기준으로 CapturePack의 플러그인 시스템을 설계하고 구현하라.
기존 CapturePack 저장소의 코드, GOAL.md, SPEC.md, ROADMAP.md, 플러그인 구조, Chrome Extension 구조를 먼저 확인하고 현재 철학을 유지한 채 변경하라.
문서와 구현이 충돌하지 않도록 포맷 및 프로토콜 문서를 먼저 갱신한 후 코드와 테스트를 수정한다.
1. 프로젝트 전제
CapturePack의 핵심 철학은 다음과 같다.
Capture context, not screenshots.

CapturePack은 버그 트래커나 외부 서비스가 아니다.
CapturePack은 사용자가 과거 화면의 특정 시간과 특정 객체를 선택하여, 사람이든 프로그램이든 이해할 수 있는 독립적인 Context 원재료를 만드는 도구다.
화면과 구조적 Context를 계속 보관
    ↓
사용자가 과거 시간 선택
    ↓
사용자가 화면상의 객체 선택
    ↓
CapturePack 폴더 저장
    ↓
필요하면 외부 시스템이 소비
CapturePack Core는 다음만 책임진다.
Replay Ring Buffer
Screenshot
Timeline Scrub
Annotation
Object Selection
Folder-first Save
Annotated Replay Rendering
CapturePack Format
MCP
Plugin Host
CapturePack Core는 다음을 직접 책임지지 않는다.
Jira Issue 관리
Redmine Ticket 관리
GitHub Issue 관리
이메일 발송
Slack / Discord 전송
워크플로 관리
담당자 및 상태 관리
서비스별 인증과 API
외부 서비스 지원은 플러그인이 맡는다.
2. 플러그인 유형
CapturePack 플러그인은 역할이 완전히 다른 두 종류로 나눈다.
CapturePack Plugin System
├─ Temporal Context Providers
└─ After Save Actions
각 타입의 정의는 다음과 같다.
Temporal Context Provider
= CapturePack Replay와 동기화된 과거 구조적 Context를 보관하고,
  특정 시간과 화면 좌표에서 객체 후보를 반환한다.

After Save Action
= 저장된 CapturePack을 입력으로 받아 외부 작업을 실행한다.
두 플러그인은 API, 생명주기, 실행 방식, 권한을 분리한다.
3. Temporal Context Provider의 본질
기존처럼 캡처 버튼을 누른 순간 Context Provider를 한 번 호출하는 구조는 잘못됐다.
사용자는 CapturePack에서 과거 30초를 탐색한다.
따라서 Chrome DOM, Windows UI, Unreal Widget과 같은 구조적 Context도 과거 시점의 상태를 복원할 수 있어야 한다.
올바른 구조는 다음과 같다.
CapturePack Replay Ring Buffer
├─ Video Ring Buffer
├─ Platform Surface Timeline
├─ Chrome DOM Temporal Buffer
├─ Windows UI Temporal Buffer
├─ Unreal Temporal Buffer
└─ Other Provider Temporal Buffers
Provider는 CapturePack과 함께 계속 실행되며 각자 자신의 Temporal Buffer를 유지한다.
CapturePack은 Provider의 데이터를 직접 수집하거나 해석하지 않는다.
Provider
= 관찰하고 기록하고 복원한다.

CapturePack
= 시간과 화면 위치를 선택한다.
4. 매 프레임 상태의 의미
Temporal Context Provider는 선택 가능한 모든 시간에서 구조적 상태를 반환할 수 있어야 한다.
하지만 매 영상 프레임마다 DOM 전체나 UI Tree 전체를 복사하도록 강제하지 않는다.
요구사항은 다음과 같다.
논리적으로는 임의의 Replay 시간에서 상태를 복원할 수 있어야 하지만, 내부 저장 방식은 Provider가 결정한다.

Provider는 다음과 같은 방식을 사용할 수 있다.

0.4초  Node 추가

Provider마다 샘플링 주기와 저장 방식은 다를 수 있다.
Core는 전체 Tree를 매 Tick마다 요구하지 않는다.
5. 공통 시간 기준
모든 Provider는 CapturePack Replay와 동일한 시간축을 사용해야 한다.
Wall Clock을 각 Provider가 독립적으로 사용하면 안 된다.
CapturePack Core가 하나의 Monotonic Session Clock을 제공한다.
interface CaptureClock {
  sessionId: string;
  nowMs: number;
  bufferStartMs: number;
  bufferEndMs: number;
}
Provider가 기록하는 모든 이벤트는 이 시간축을 사용한다.
Replay Frame Time
DOM Event Time
UI Automation Event Time
Window Z-order Time
Annotation Time
모두 동일한 timeMs 기준으로 비교할 수 있어야 한다.
Provider가 정확한 시점의 상태를 제공할 수 없는 경우 가장 가까운 샘플을 반환하되, 오차도 함께 반환한다.
interface TemporalAccuracy {
  requestedTimeMs: number;
  materializedTimeMs: number;
  errorMs: number;
  exact: boolean;
}
6. Temporal Context Provider 생명주기
Core는 Provider에 Ring Buffer 생명주기 이벤트만 제공한다.
interface TemporalContextProvider {
  id: string;
  name: string;
  version: string;
  protocolVersion: string;
  type: "temporal-context-provider";

  onBufferStart?(
    context: BufferStartContext
  ): Promise<void>;

  onTick?(
    context: BufferTickContext
  ): Promise<void>;

  onPrune?(
    context: BufferPruneContext
  ): Promise<void>;

  onFreeze?(
    context: BufferFreezeContext
  ): Promise<void>;

  materialize(
    context: MaterializeContext
  ): Promise<ProviderState>;

  getSurfaceClaims(
    context: SurfaceClaimContext
  ): Promise<ProviderSurfaceClaim[]>;

  hitTest(
    context: HitTestContext
  ): Promise<ContextCandidate[]>;

  track(
    context: TrackContext
  ): Promise<ObjectTrack>;

  export(
    context: ProviderExportContext
  ): Promise<ProviderExportResult>;
}
7. Provider 이벤트 정의
onBufferStart
새로운 Capture Session이 시작됐음을 알린다.
interface BufferStartContext {
  sessionId: string;
  startedAtMs: number;
  retentionMs: number;
}
Provider는 자신의 임시 Temporal Buffer를 초기화한다.
onTick
CapturePack의 현재 Monotonic Time을 제공한다.
interface BufferTickContext {
  sessionId: string;
  timeMs: number;
  bufferStartMs: number;
  bufferEndMs: number;
}
onTick은 전체 상태 저장 명령이 아니다.
Provider는 자신의 특성에 따라 필요한 경우에만 샘플링한다.
예:
Chrome DOM
= Event-driven + Bounds 10Hz

Windows UI
= Event-driven + Bounds 10~15Hz

Unreal
= Engine Tick 또는 Widget 변경 이벤트
onPrune
Ring Buffer 범위를 벗어난 데이터를 제거하도록 요청한다.
interface BufferPruneContext {
  sessionId: string;
  beforeTimeMs: number;
}
Provider는 다음을 제거한다.
오래된 Checkpoint
오래된 Delta
오래된 Geometry Sample
오래된 Object Track
다만 현재 상태을 복원하기 위해 필요한 직전 Checkpoint는 유지할 수 있다.
onFreeze
사용자가 Capture 단축키를 눌러 Replay 범위를 고정했음을 알린다.
interface BufferFreezeContext {
  sessionId: string;
  range: {
    startMs: number;
    endMs: number;
  };
}
Provider는 해당 범위의 데이터가 Prune되지 않도록 고정한다.
CapturePack Editor가 닫히거나 저장이 완료될 때까지 이 범위를 유지한다.
8. 상태 복원
사용자가 Timeline을 이동할 때 Core는 Provider에 해당 시간의 Context를 요청한다.
interface MaterializeContext {
  sessionId: string;
  timeMs: number;
}
interface ProviderState {
  providerId: string;
  timeMs: number;
  accuracy: TemporalAccuracy;
  surfaces: ProviderSurfaceClaim[];
  metadata?: Record<string, unknown>;
}
materialize()는 해당 시점의 전체 구조를 UI에 모두 전송할 필요는 없다.
Provider 내부에서 해당 시점의 상태를 준비하거나 캐시하는 용도로 사용할 수 있다.
실제 객체 선택은 hitTest()를 사용한다.
9. CapturePack Core의 Surface Timeline
Provider 간 충돌을 해결하기 위해 단순한 pluginPriority 숫자를 사용해서는 안 된다.
예:
앞쪽에 일반 Windows 창
뒤쪽에 창 모드 Unreal 게임
동일한 좌표를 모든 Provider에 묻는다면:
Windows UI Provider
→ 버튼 후보 반환

Unreal Provider
→ Widget 후보 반환
둘 다 해당 좌표에 객체가 있다고 판단할 수 있다.
하지만 사용자가 실제로 보는 것은 앞쪽 Windows 창이다.
따라서 Provider를 조회하기 전에 해당 시간의 화면 Surface Stack을 먼저 복원해야 한다.
이를 위해 CapturePack Core는 최소한의 플랫폼 기능인 Platform Surface Timeline을 자체적으로 가진다.
이 기능은 Windows UI 객체를 해석하는 Provider가 아니다.
역할은 오직 다음뿐이다.
Top-level Window
HWND
Process ID
Window Bounds
Client Bounds
Z-order
Visibility
Minimized 상태
Foreground 상태
Visible Region
Surface Ownership
Surface Timeline 역시 Replay Ring Buffer와 동일한 시간축으로 기록한다.
시간 T에서
어떤 Window가
어떤 위치와 크기로
어떤 Z-order에 있었는지
를 복원할 수 있어야 한다.
CapturePack Editor가 열린 이후의 현재 Desktop이 아니라, 캡처 이전 과거 시점의 Desktop Surface 상태를 사용해야 한다.
10. Surface Resolver
사용자가 시간과 화면 좌표를 선택하면 Core는 먼저 Surface Resolver를 실행한다.
interface SurfaceQuery {
  sessionId: string;
  timeMs: number;
  point: ScreenPoint;
}
interface SurfaceInfo {
  surfaceId: string;
  hwnd?: string;
  processId?: number;
  bounds: Rect;
  visibleRegion?: Rect[];
  zOrder: number;
  visible: boolean;
  minimized: boolean;
  executableName?: string;
  windowTitle?: string;
}
Surface Resolver는 해당 좌표의 Surface Stack을 반환한다.
Cursor: (840, 420)

Surface Stack
1. Notepad HWND
2. Unreal Game HWND
3. Desktop
기본 선택 대상은 사용자가 실제로 보고 있는 최상단 Visible Surface다.
Topmost Visible Surface
→ Notepad
뒤쪽 Unreal Surface는 기본 후보에서 제외한다.
다만 사용자가 필요할 때 Surface Stack을 순환할 수 있도록 데이터는 유지한다.
11. Provider Surface Claim
각 Provider는 자신이 어느 Surface와 어느 영역을 담당하는지 선언한다.
interface ProviderSurfaceClaim {
  providerId: string;
  surfaceId: string;

  hwnd?: string;
  processId?: number;

  region: Rect;

  authority:
    | "application-native"
    | "document-native"
    | "accessibility"
    | "window";

  confidence: number;
}
예를 들어 Chrome 창 하나는 여러 Provider가 담당할 수 있다.
Chrome HWND
├─ Chrome DOM Provider
│  └─ Web Content Viewport
│
└─ Windows UI Provider
   └─ 주소창, 탭, 메뉴, 브라우저 프레임
커서가 웹페이지 본문에 있으면 Chrome DOM Provider가 Surface Claim을 가진다.
커서가 주소창이나 탭에 있으면 Chrome DOM Provider의 Region 바깥이므로 Windows UI Provider가 담당한다.
Provider가 무조건 Window 전체를 자신의 영역이라고 주장해서는 안 된다.
12. 객체 Hit Test
Core가 최상단 Surface를 결정하면 해당 Surface를 담당하는 Provider에만 객체 후보를 요청한다.
interface HitTestContext {
  sessionId: string;
  timeMs: number;
  point: ScreenPoint;
  surface: SurfaceInfo;
}
Provider는 해당 위치의 객체 후보를 반환한다.
interface ContextCandidate {
  providerId: string;
  surfaceId: string;

  objectId: string;
  objectType: string;
  name?: string;

  bounds: Rect;
  depth: number;

  authority:
    | "application-native"
    | "document-native"
    | "accessibility"
    | "window";

  confidence: number;

  visible: boolean;
  occluded: boolean;

  parentId?: string;
  metadata?: Record<string, unknown>;
}
예:
Chrome DOM Provider

button#save
div.toolbar
body
document
Provider 내부에서는 일반적으로 가장 깊고 구체적인 객체가 우선이다.
13. Provider 간 후보 우선순위
전역적인 플러그인 숫자 우선순위를 첫 기준으로 사용하지 않는다.
다음 순서로 후보를 정렬한다.
1. Surface Visibility와 Z-order
2. 해당 Surface에 대한 Provider Claim
3. Provider의 Semantic Authority
4. 객체의 Semantic Depth
5. Provider Confidence
6. 사용자 선호도
기본 Authority 순서는 다음과 같다.
Application-native
→ Document-native
→ Accessibility
→ Window
→ Manual Rectangle
예:
Unreal 게임
Unreal Provider
→ UWidget, Actor, UObject

Windows UI Provider
→ Render Surface 또는 HWND
Unreal Provider가 더 구체적이므로 우선한다.
Chrome 웹 콘텐츠
Chrome DOM Provider
→ HTML Element, Selector, Attribute

Windows UI Provider
→ Document, Pane
Chrome DOM Provider가 우선한다.
일반 Windows 앱
Application-native Provider 없음
→ Windows UI Automation Provider 사용
어떤 Provider도 객체를 반환하지 못함
Manual Rectangle
로 자연스럽게 폴백한다.
14. 후보를 제거하지 말 것
우선순위가 낮은 후보도 버리지 않는다.
예:
기본 선택
[DOM] button#save

다른 후보
[UIA] Button "Save"
[Window] Chrome
사용자는 동일 위치의 후보를 순환할 수 있어야 한다.
권장 입력:
Click
→ 최적 후보 선택

Tab
→ 다음 객체 후보

Shift + Tab
→ 이전 객체 후보

Alt + Click
→ 뒤쪽 Surface 후보 순환
초기 버전에서는 Alt + Click을 구현하지 않아도 되지만, 후보 모델과 Surface Stack 데이터는 이를 지원할 수 있어야 한다.
기본 동작은 항상 사용자가 실제로 보는 최상단 객체와 일치해야 한다.
15. 선택 알고리즘
최종 객체 선택 알고리즘은 다음과 같다.
1. 사용자가 Replay 시간 선택
2. 사용자가 화면 위치 선택
3. 해당 시간의 Surface Stack 복원
4. 해당 좌표의 최상단 Visible Surface 결정
5. 해당 Surface에 Claim을 가진 Provider 조회
6. 각 Provider에 hitTest 요청
7. 후보를 Authority, Depth, Confidence로 정렬
8. 첫 후보를 기본 선택
9. 나머지는 Candidate Stack으로 유지
10. 후보가 없으면 Manual Rectangle 사용
의사 코드:
const surfaceStack = surfaceResolver.resolve({
  sessionId,
  timeMs,
  point,
});

const activeSurface = surfaceStack.firstVisible();

const providers = pluginHost.findProvidersForSurface(
  activeSurface,
  point,
);

const candidates = await Promise.all(
  providers.map(provider =>
    provider.hitTest({
      sessionId,
      timeMs,
      point,
      surface: activeSurface,
    }),
  ),
);

const ordered = candidates
  .flat()
  .filter(candidate => candidate.visible && !candidate.occluded)
  .sort(compareCandidates);
정렬 우선순위:
function compareCandidates(
  a: ContextCandidate,
  b: ContextCandidate,
): number {
  return (
    compareSurfaceVisibility(a, b) ||
    compareAuthority(a, b) ||
    compareSemanticDepth(a, b) ||
    compareConfidence(a, b) ||
    compareUserPreference(a, b)
  );
}
16. 객체 Tracking
사용자가 객체 후보를 Annotation Target으로 선택하면 CapturePack은 Provider의 Object ID를 저장한다.
interface SemanticAnnotationTarget {
  providerId: string;
  surfaceId: string;
  objectId: string;
}
그 후 Provider에 해당 객체의 시간별 Bounds를 요청한다.
interface TrackContext {
  sessionId: string;
  objectId: string;
  range: {
    startMs: number;
    endMs: number;
  };
}
interface ObjectTrack {
  objectId: string;
  samples: Array<{
    timeMs: number;
    bounds: Rect;
    visible: boolean;
  }>;
  createdAtMs?: number;
  removedAtMs?: number;
}
Tracked Annotation은 객체의 Bounds를 따라 이동한다.
객체가 사라지면 Annotation Lifetime도 자동으로 종료한다.
객체 생성
→ Annotation 표시 가능

객체 이동
→ Annotation Bounds 이동

객체 제거
→ Annotation 자동 종료
17. Provider Export
Provider의 Temporal Buffer 전체를 CapturePack 폴더에 그대로 복사할 필요는 없다.
Temporal Buffer는 편집 중 과거 상태를 탐색하기 위한 작업 데이터다.
저장 시에는 선택한 Replay 범위와 선택한 객체에 필요한 Context만 Export한다.
권장 출력:
plugins/<provider-id>/
├─ meta.json
├─ context.json
├─ selected-object.json
├─ object-track.json
└─ timeline.json
Chrome 예:
plugins/chrome-dom/
├─ meta.json
├─ page.json
├─ dom-at-selected-time.json
├─ selected-element.json
└─ element-track.json

19. Temporal Provider의 공식 범위
CapturePack 프로젝트가 직접 유지할 공식 Temporal Context Provider 범위는 작게 유지한다.
기본 방침:
Official
- Chrome Web DOM

Core Platform Infrastructure
- Windows Surface Timeline
- Surface Resolver

Community / External
- Windows UI Automation Objects
- Unreal
- Unity
- Other Applications
Windows Surface Timeline은 Provider가 아니라 객체 충돌을 해결하기 위한 Core 플랫폼 기능이다.
CapturePack Core는 Windows UI Tree나 Unreal Object Tree를 직접 해석하지 않는다.
20. After Save Action
After Save Action은 저장된 CapturePack을 소비해 외부 작업을 실행한다.
CapturePack Folder Saved
    ↓
After Save Pipeline
    ↓
HTTP / Jira / Redmine / Email / Script / 기타
예:
Create ZIP
HTTP POST
Webhook
Jira
Redmine
GitHub Issue
GitLab Issue
Email
Discord
Slack
S3 Upload
Custom Script
Custom Executable
CapturePack Core는 서비스별 기능을 구현하지 않는다.
Core는 After Save Action을 실행할 수 있는 공통 프로토콜만 제공한다.
21. After Save Action API
interface AfterSaveAction {
  id: string;
  name: string;
  version: string;
  protocolVersion: string;
  type: "after-save-action";

  requirements: AfterSaveRequirements;

  execute(
    context: SavedPackContext,
    settings: Record<string, unknown>,
  ): Promise<AfterSaveActionResult>;
}
interface AfterSaveRequirements {
  requiredState:
    | "metadata-ready"
    | "source-ready"
    | "annotated-replay-ready"
    | "complete";

  requiresZip?: boolean;
  requiresAnnotatedReplay?: boolean;
}
interface SavedPackContext {
  packId: string;
  packPath: string;
  manifestPath: string;

  snapshotPath?: string;
  replayPath?: string;
  annotatedReplayPath?: string;
  reportPath?: string;
  readmePath?: string;
  zipPath?: string;

  manifest: CapturePackManifest;
}
interface AfterSaveActionResult {
  status: "success" | "failed" | "skipped";

  message?: string;
  externalId?: string;
  externalUrl?: string;

  generatedFiles?: string[];
  warnings?: string[];

  error?: {
    code: string;
    message: string;
  };
}
22. Pack 준비 상태
Annotated Replay는 백그라운드에서 렌더링될 수 있다.
따라서 모든 Action을 동일한 시점에 실행하면 안 된다.
Pack 상태를 단계별로 구분한다.
captured
metadata-ready
source-ready
annotated-replay-rendering
annotated-replay-ready
complete
예:
HTTP Metadata Action
→ metadata-ready에서 실행

Jira Attachment Action
→ annotated-replay-ready에서 실행

Create ZIP
→ complete에서 실행
Action은 자신이 필요한 상태와 파일을 선언한다.
23. After Save Pipeline
여러 Action을 순서대로 실행할 수 있어야 한다.
예:

2. HTTP POST

4. Send Discord Message

초기 범위에 포함하지 않는다.
복잡한 조건식

반복문

클라우드 자동화 서비스
After Save Action은 단순하고 재실행 가능해야 한다.
24. After Save 실패 정책
After Save Action 실패가 CapturePack 저장을 실패로 바꾸면 안 된다.
CapturePack Folder
= 이미 정상 저장된 원본

After Save Action
= 저장 이후의 부가 작업
예:
Saved successfully

After Save Actions
✓ ZIP created
✓ HTTP sent
✕ Jira failed
✓ Discord sent
실패한 Action만 다시 실행할 수 있어야 한다.
[ Retry Jira ]
Pipeline의 Continue on Failure 설정에 따라 이후 Action을 계속 실행할 수 있다.
25. 재실행과 멱등성
After Save Action은 저장 직후뿐 아니라 나중에도 다시 실행할 수 있어야 한다.

    ↓

    ↓
Jira / HTTP / Mail / Script

+

33. 완료 기준
다음 조건을 만족해야 한다.
Replay 시간과 Provider 시간이 동일한 Clock으로 동기화된다.

Provider는 과거 시점의 Context를 복원할 수 있다.

사용자가 선택한 시간과 좌표에서 객체 후보를 얻을 수 있다.

뒤쪽 Window의 Provider가 앞쪽 Window보다 먼저 선택되지 않는다.

같은 Surface의 여러 객체 후보를 순환할 수 있다.

Tracked Annotation이 객체의 위치와 수명을 따라간다.

Provider 실패가 CapturePack 저장을 막지 않는다.

After Save Action 실패가 CapturePack 저장을 무효화하지 않는다.

Chrome DOM이 공식 Temporal Context Provider로 작동한다.

다른 개발자가 별도의 Provider나 After Save Action을 구현할 수 있다.
34. 최종 철학
CapturePack Core
= 시간과 화면을 제공한다.

Temporal Context Provider
= 해당 시간의 구조적 Context를 복원한다.

Surface Resolver
= 사용자가 실제로 보고 있던 Surface를 결정한다.

CapturePack Editor
= 시간과 객체를 선택한다.

After Save Action
= 완성된 CapturePack을 외부에서 사용한다.
최종 문장:
CapturePack records the visual timeline.
Temporal Context Providers preserve the semantic timeline.
The user chooses the time and target.
After Save Actions decide where the resulting context goes.
